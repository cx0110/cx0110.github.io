> **一句话结论**：多 Agent 不代表先进，单 Agent 也不是银弹 —— 关键是**架构边界有没有证据支持**。先度量，一次只改一处。

很多团队做 Agent 都会走到同一个路口：业务能力越来越多，系统提示词越来越长，于是开始拆。路由一个 Agent，规划一个 Agent，售后、物流、账单各自再拆一个 Agent。最后系统看起来井井有条，实际运行却可能是另一回事 —— 每一次交接都在丢信息，每一次调用都在增加延迟，每一个团队还在往提示词里追加自己的规则。

Anthropic 在这篇文章里给出了一个值得重视的判断：**很多企业的子 Agent 不是太少，而是太多。**

在多个企业部署的对比中，单 Agent 配合 Skills，经常在质量上超过「一个巨型提示词」和「多子 Agent」两种设计，同时还能降低任务成本和延迟。

但注意，这不是一篇反对多 Agent 的文章。它真正讨论的是：**哪些子 Agent 应该收回主循环，哪些子 Agent 值得继续保留。**

## 一、你的 Agent 架构，可能只是组织架构的投影

很多公司的建设路径非常相似：每个业务团队负责一项能力，于是每个团队先做一个自己的 Agent；平台团队再在最上面加一个编排器，负责识别意图、分发任务和汇总结果。

这个方案在**组织协作上最省事**，在**系统运行上却可能很贵**。通常带来五类问题：

**第一，上下文在交接中丢失。** 子 Agent 收到的是摘要，返回的还是摘要。原本完整的用户意图、中间结果和异常信息，经过几次转述后，保真度不断下降。

**第二，子 Agent 不断增殖。** 每个团队都交付自己的子 Agent，最后可能出现大量能力重叠、标准不一、无人整体负责的模块。

**第三，系统提示词变成拼盘。** 每个团队都往里面加几条规则。短期看解决了局部问题，长期看可能形成相互冲突的指令，连回答风格都难以统一。

**第四，评测只优化局部。** 每个团队都证明自己的子任务做得不错，却没有人对最终任务是否完成负责。局部分数越来越漂亮，整体体验未必变好。

**第五，延迟层层叠加。** 每多一次子 Agent 调用，就多一层模型循环和结果交接。原文提到，一位客户将多 Agent 运行框架与单 Agent 循环进行对比，**后者的运行速度约为前者的两倍**。

> 一句话总结：**组织可以按团队划分，Agent 不应机械地照抄组织架构。**

## 二、单主循环真正解决的，是上下文被切碎的问题

目标形态并不神秘：**一个模型，一个上下文窗口，一个开放式工具循环。**

模型自己制定计划，发起工具调用，查看结果，再根据新信息修改计划。每一轮可以批量调用工具，由运行层并行执行，并把原始结果交还同一个模型。

与传统编排器模式最大的区别是：**制定计划的模型，也是执行计划的模型。** 它不再只是按照预先写死的流程往前走，而是能够根据现场情况调整下一步。

三个优势：

### 1. 共享上下文，减少信息损耗

主 Agent 能看到此前每一步的结果，就更容易把不同线索联系起来。相比多个子 Agent 分别返回摘要，完整上下文通常更有利于形成综合判断，也减少了反复交接造成的信息损失。

### 2. 按需加载，避免上下文膨胀

单主循环并不意味着把所有资料重新塞进一个超长提示词。Skills 和工具可以先只展示简短说明，确实需要时再加载完整内容。领域流程、产品规则、工具定义，都不必从一开始就占满上下文。

Anthropic 表示，面向能力更强的模型，**Claude Code 的系统提示词缩减超过 80%**，其中包含 Skills 和工具按需加载带来的缩减。

### 3. 把规划能力交还给模型

过去需要依靠意图分类器、固定推理流程和独立规划模块完成的工作，如今越来越多可以由模型直接承担。

工程系统的角色也随之变化：**它不再替模型决定每一步，而是提供工具、数据、预算和安全边界。**

## 三、单主循环 ≠ 一个更大的 Prompt

这是最容易被误读的地方。真正合理的单主循环，依然需要清晰分层：

| 层 | 职责 | 迁移什么进来 |
|---|---|---|
| **Skills** | 领域方法 | 专家子 Agent 提示词中的工作步骤、执行顺序、业务规则和判断方式 |
| **Tools** | 真实动作 + 硬约束 | 查询实时数据、操作业务系统、返回固定结构；权限校验、参数验证、审批闸门 |
| **知识库** | 按需查询的参考资料 | 政策文件、指标定义、产品规格 —— 不必长期驻留系统提示词 |
| **运行层** | 预算和安全边界 | 轮次上限、成本预算、写入限制、并行工具执行 |

> **Tools 那行最容易被忽略**：权限校验、参数验证和审批闸门，应该由工具或运行层执行，**而不是只靠提示词劝说模型**。

工具设计也不能简单理解为「每个 API 包一层」。原文建议**按用户意图组织工具** —— 因为系统提示词中的工具定义**超过 30 到 50 个后，工具选择效果往往会下降**。

所以，单主循环不是回到一个巨型 Prompt，而是让模型在统一上下文中，按需调用领域知识、工具和业务规则。

## 四、这三类子 Agent，别急着收回

文章并没有把单主循环当成所有场景的标准答案。以下三种情况，子 Agent 依然很有价值：

**第一，上下文膨胀已经造成可测量的性能下降。** 如果单 Agent 装入过多无关信息，回答质量明显变差，独立上下文就有实际意义。

**第二，多个任务需要并行处理。** 各项任务彼此独立，需要全新的上下文窗口，而且完成后可以丢弃中间过程。

**第三，工具选择或指令冲突难以解决。** 如果单 Agent 经常选错工具，或者不同领域的指令放在一起会相互干扰，保留边界可能更稳妥。

此外，**独立研究路径、接口清晰的独立组件和黑盒验证**，也天然适合子 Agent。

> **关键仍然是：按上下文边界拆分，而不是按团队名称或问题类型拆分。**

如果决定保留子 Agent，可以优先让主 Agent 将它**作为工具调用**，由主 Agent 继续持有用户对话。只有子 Agent 必须直接与用户交流时，才考虑完全交接。

## 五、不要推倒重来，按这五步迁移

对于已经运行在生产环境的多 Agent 系统，思路非常务实：

**第一步，先建立端到端评测。** 不要急着改架构，先弄清楚现在的系统到底做得怎么样。可以由中央团队维护一套共享的端到端评测，各业务团队再为自己负责的 Skill 配套小型评测。**即使一开始只有 10 个高质量样例，也足以启动。**

> 保留编排器时关注路由是否选对了子 Agent；合并之后检查主 Agent 是否加载了正确的 Skill、调用了正确的工具，最终再逐步转向任务完成度评测。

**第二步，先合并高度耦合的领域 Agent。** 优先观察调用最频繁、交接最多的子 Agent。如果两个专家经常连续处理同一个请求，依赖彼此的输出，或者访问相同的数据，它们就很可能应该共享上下文。

**第三步，把暂时保留的子 Agent 改成工具调用。** 这一步不必立即重写子 Agent。先让主 Agent 统一持有对话，通过固定输入输出结构调用它们。这样既能为后续对比建立基线，也能减少完全交接带来的上下文损失。

**第四步，一次只收回一个子 Agent。** 将子 Agent 的提示词转化为 Skill，将它调用的 API 转化为 MCP 工具，然后比较合并前后的评测结果。**不要只看平均分，还要看具体哪些任务从通过变成失败。**

> 🔴 原文的示例很实在：一次合并虽然降低了延迟，却破坏了原本正确的流程 —— 主 Agent 拿着订单查询工具直接回答，**跳过了本应由物流专家提供的送达日期**。这个问题**运行两次才暴露一次**。
> 因此，每一条生产链路、每一项不可违反的规则，都应该进入评测，同一个任务也需要重复运行。

**第五步，重新划分团队职责。** 领域团队不必继续各自拥有一个 Agent，但可以拥有自己的 Skills、工具和配套评测。一个小型中央团队负责系统提示词、端到端质量和新增能力审核，避免单主循环再次演变成无人治理的提示词拼盘。

## 六、判断

Agent 架构正在从**堆模块**，进入**删复杂度**的阶段。

删掉的不是能力，而是**重复规划、有损交接，以及没有必要的上下文隔离**。

多 Agent 不代表先进，单 Agent 也不是银弹。真正重要的是，**架构边界有没有证据支持**。

> 最值得记住的原则：**先度量，一次只改一处，留下经得起检验的。**

如果你今天已经在维护一套多 Agent 系统，不必推倒重来：先找出一个调用最频繁、与其他 Agent 耦合最深的子 Agent，准备十个端到端样例，尝试将它改造成 Skill 加工具。别急着争论哪种架构更先进，**先让评测结果说话**。
