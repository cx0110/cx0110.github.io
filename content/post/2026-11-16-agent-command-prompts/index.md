> **一句话结论**：这 10 句不是「提问技巧」，而是**一套把 agent 从「执行者」变成「质疑者 + 复盘者」的工作方法** —— 每一句都在对抗 agent 最典型的失败模式。

作者的说明：

> 今天无聊，正好让 Agent 给我翻了一下最近两个月，我指挥 Agent 干活，最爱说的几句 Prompt，我觉得还挺有意思也挺有用的，确实都是我自己沉淀下来觉得最好用的，也给大家分享一下。

## 一、10 条原文

**1. 从第一性原理出发，找到最本质原因，修复一下。**

**2. 先问一些不清晰的问题，对齐我的喜好，然后再出 3 版方案。**

**3. 不要默认我提出的问题定义就是正确的。** 你先分析我真正想解决的底层需求，判断我有没有把症状误认为原因、把手段误认为目标。如果存在更值得解决的问题，直接指出来。

**4. 不要只考虑这个改动产生的直接效果。** 继续推演它的二阶、三阶影响，尤其关注对其他模块、用户行为、系统复杂度和长期维护成本的潜在影响。

**5. 其他领域里有没有类似的方案，用跨领域的方式全面思考，找到最优解。**

**6. 先假设你当前认为最合理的方案是错误的。** 站在最强反对者的角度，寻找能够推翻它的证据、反例和边界情况。然后重新评估方案，看看有没有更好的解法。

**7. 深入分析整个代码库的 Git 历史、关键 PR 和架构演变过程。** 找出哪些设计是有意为之，哪些是历史遗留，哪些是为了解决已经不存在的问题而引入的。识别可以安全移除的历史包袱。

**8. 假设明天有一个完全不了解项目、但是能力很强的工程师来接手。** 请评估他理解整个项目需要付出的认知成本，找出那些命名混乱、抽象过度、职责不清晰、需要大量上下文才能理解的代码，并提出简化方案。

**9. 全面分析最近 XX 天里的所有的 PR，找出最慢的那几个，看看有没有导致卡顿、可以优化的地方。**

**10. 全面复盘最近 XX 时间的 Bug、返工、回滚和重复修改。** 不要只统计发生了什么，要分析这些问题背后有没有共同的根因。把能够预防的共性问题沉淀成项目规则、自动化或者 Skill，避免我们反复支付同样的成本。

## 二、我的解读：这 10 句在对抗什么

把 10 句按**对抗的 agent 失败模式**重新归类，比按原顺序读更有用：

| # | 原句 | 对抗的失败模式 | 本质动作 |
|---|---|---|---|
| 1 | 第一性原理 | **头痛医头** | 从现象层降到机制层 |
| 2 | 先问 + 出 3 版 | **猜错偏好就开做** | 先对齐，再展开 |
| 3 | 不要默认我的问题定义正确 | **执行错误的目标**（最危险） | 反向诊断需求 |
| 4 | 推演二阶三阶影响 | **局部正确、全局破坏** | 系统思维 |
| 5 | 跨领域找类似方案 | **重复发明轮子** | 横向检索 |
| 6 | 假设最优方案是错的 | **第一答案的引力** | 红队自查 |
| 7 | 挖 Git 历史 | **把历史遗留当设计意图** | 考古 |
| 8 | 假设新人接手 | **认知债务** | 可读性审计 |
| 9 | 分析最慢的 PR | **只做增量不做体检** | 性能复盘 |
| 10 | 复盘 Bug 找共因 + 沉淀 | **同一个坑反复踩** | 知识沉淀闭环 |

### ⭐ 第 3 条和第 10 条是最高价值的

- **第 3 条** —— 「我提出的问题定义不一定正确」是**唯一一条直接挑战用户意图的 prompt**。多数人不敢写，因为怕 agent「自作主张」。但恰恰是这一条，把 agent 从「高级搜索框」变成了「能顶回去的同事」。
- **第 10 条** —— 前半句是复盘，后半句「**沉淀成项目规则、自动化或者 Skill**」是闭环。这正是 agent 工作流的正确终局：**每次返工都要变成可复用的资产，而不是下一次的对话历史**。

### 值得单独标注的三个

**#6 红队自查**：不是让 agent 自我批评（agent 很容易表演式反思），而是**指定一个角色**（最强反对者）并要求**给出可推翻的证据**。这个措辞比「请认真检查一下」有效得多。

**#8 新人接手视角**：这是**认知成本**这个概念的可操作化 —— 用「一个强能力但完全不了解项目的人」当尺子，量出代码库的**可理解性债务**。

**#7 Git 历史考古**：这是把 **git log 当知识源**用 —— agent 通常只读当前代码，看不到「这个设计为什么长成这样」。这条 prompt 强迫它去读历史。

## 三、可直接抄的模板

把 10 条压成一个可复用的 prompt 骨架：

```
【目标对齐】先问我不清楚的地方，对齐偏好，再出 3 版方案供选。
【需求校验】不要默认我的问题定义正确。判断我有没有把症状误认为原因、把手段误认为目标；有更值得解决的问题直接说。
【根因分析】从第一性原理出发，找到最本质原因再修。
【影响推演】不只看直接效果，推演二阶、三阶影响（其他模块 / 用户行为 / 系统复杂度 / 长期维护成本）。
【横向借鉴】其他领域有没有类似方案？跨领域找最优解。
【红队自查】先假设当前方案是错的，站在最强反对者角度找证据、反例、边界情况。
【历史考古】读 Git 历史和关键 PR，分清「有意设计 / 历史遗留 / 为已不存在的问题而引入」，指出可安全移除的包袱。
【可读性审计】假设明天有个能力很强但完全不了解项目的工程师接手，评估他的认知成本，指出命名混乱 / 抽象过度 / 职责不清的地方。
【性能体检】分析最近 N 天的 PR，找出最慢的几个和卡顿原因。
【复盘沉淀】复盘最近 N 时间的 Bug / 返工 / 回滚 / 重复修改，找共因，沉淀成项目规则、自动化或 Skill。
```

### 分场景裁剪（我的建议）

| 场景 | 用哪几条 |
|---|---|
| **修 bug** | 1 · 3 · 4 · 6 · 7 |
| **做新功能** | 2 · 3 · 4 · 5 · 6 |
| **重构 / 清理** | 4 · 7 · 8 · 10 |
| **性能优化** | 4 · 9 · 10 |
| **接手新项目** | 5 · 7 · 8 |

> **不要一次全上** —— 10 条全给 agent 是噪声，实际效果反而下降（同 Anthropic 那篇讲的「工具定义超过 30-50 个后选择效果退化」的同构问题）。

## 四、我的判断

**这套 prompt 的价值不在句式，在「它要求 agent 做判断而不是执行」。**

多数人用 agent 的方式是「把需求说清楚 → 等结果」。这 10 条的共同点是**都在给 agent 加约束**：要求它质疑、要求它推演、要求它跨领域、要求它自证、要求它沉淀。**用 agent 的上限 = 你愿意给它多少判断权。**

**诚实的边界**：第 3 条（质疑用户）**只在信任度高的时候才划算** —— 如果你的领域知识不如 agent，它「纠正」你的方向可能是纯噪声。作者敢用这 10 条，说明他的场景是**长期协作、agent 已经积累了他项目的上下文**。

**和 Skill 的关系**：第 10 条明确说「沉淀成项目规则、自动化或者 Skill」—— **这 10 条 prompt 本身就是一份极好的 Skill 素材**。它们不是 10 个孤立技巧，而是一套完整的「如何指挥 coding agent」方法论。

- **对位 11-15 Vibe Coding 四步流程那篇**：那篇是「一个人 + 一个 agent 做完一个 App」的流程，本篇是「指挥 agent 的 10 句话」—— **流程层 + 指令层的组合**
- **对位 10-22 prompt-optimizer（Go 专题）**：那篇讲「提示词改写工具暴露的真问题」，本篇是**真实用户沉淀的 prompt 库** —— 理论和实践的对照
- **对位 09-02 确定性 Harness（左昊 / 腾讯云）**：那篇的核心是「结论必须可验证可追溯」，本篇第 6 条「找出能够推翻它的证据」是同一诉求的**用户侧版本**
- **对位 10-21 Agent 评测方法论（孙敦灿）**：那篇讲「把不稳定智能行为收敛成可发布工程质量」，本篇第 10 条「把共性问题沉淀成规则/自动化/Skill」= **从个人用法到工程化治理的过渡**
- **⭐ 最强的对位 —— 11-15 Scrapling 的官方 Agent Skill**：Scrapling 直接提供 Agent Skill 作为分发单位；本篇第 10 条说「把共性问题沉淀成 Skill」—— **同一个趋势的两端：一边是供给（现成的 skill），一边是需求（自己沉淀 skill）**
